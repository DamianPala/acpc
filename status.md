**Incident record, corrected 2026-08-10 — there was no dispatch failure.** During Wave 2 six builder dispatches were cancelled across three rounds, and I diagnosed it in turn as an external `pgrep` sweep, a self-cancellation hazard, and a flaky dispatch channel. **S3a landed 2026-08-10: replay is consumed silently, and a cold resume prefers `session/resume`.** ACP requires an agent to replay the whole conversation during `session/load`, and acpc handled that replay two different ways. On the daemon path `mux.bind` ran *after* the load and the multiplexer drops updates for unbound sessions, so replay was discarded — the right outcome reached by accident. On the direct-spawn path the client is attached at spawn, *before* the load, so replayed agent messages flowed into `answer.md` and the transcript: a cold `continue` there prepended the entire previous conversation to the one file a caller reads for the answer. Both routes now go through an explicit replay guard on `AcpcClient`, so silence is a promise rather than a side effect, and the collected user messages are kept in a sink for the verification half to consume. A cold resume now prefers `session/resume` where the adapter advertises it, falling back to `session/load`; observable behavior is identical, and it is what keeps `continue` working when ACP v2 removes `session/load`.

The review was worth more than the implementation. It proved the guard airtight rather than arguing it: traced the ACP library's dispatch to show that one `asyncio.sleep(0)` really does reschedule the caller behind every already-queued notification task, then built a stress adapter replaying 400 chunks across many socket reads and measured zero leakage over ten runs, against 400 leaked chunks with the guard neutralised. It also found the one real weakness — `test_cold_load_resume_reapplies_model_and_effort` did not pin what it claimed. It exists because codex-acp#343 resets model and effort during `session/load` and acpc survives only by re-applying them *afterwards*; but the mock never modelled the reset, so hoisting `apply_call_options` above the restore kept the suite green while silently breaking cold resume against the real adapter. The mock now clears model and effort on load, faithful to the vendor bug, and the mutation confirms the test fails on the wrong ordering.

Also from review: the capability error now names both routes ("an adapter that can restore a session — ACP session/resume or session/load"), since accepting either made the old loadSession-only wording incomplete. Worth knowing for later: `session/resume` is registered as unstable in agent-client-protocol 0.11.1, so no adapter built on that library advertises it yet — the new branch is correct but dormant in the field.

**A second post-landing find, from Damian's manual test:** `--permissions prompt` on a real TTY never asked — every out-of-policy request came back denied. `_tty_permission_prompt` opened `/dev/tty` once in `"r+"`, and Python rejects that handle as not seekable with an `io.UnsupportedOperation` — an `OSError`, so the function's own `except OSError: return False` read the failure as a refusal. ## Backlog (post-0.4)

- **The daemon re-derives a turn's env from the entry file, and only a cold adapter notices.** Slice A pinned SPEC's five resolved fields to the dispatch payload; `adapter_environment` reads `declared_env` and `env_passthrough` from the fresh lookup instead, and the payload carries neither. Mostly inert: env is read only at `AdapterHost.ensure` (`daemon.py:207`), which returns the warm connection untouched, and `call_target` keys targets on `declared_env`, so a fresh `run` after an edit routes to a different daemon and stays consistent. The one live case is `continue` after an `[env]` edit: the client computes the target from the *stored* env (`resolution_from_session` builds its entry entirely from `meta.json`) and lands on the old target, where a cold daemon then spawns the adapter with the *live* env. So restarting the daemon does not avoid this, it is what triggers it. Not a SPEC violation — SPEC:154 promises only the five — and no policy evasion, since env is the provider switch. Fix if it ever bites: carry env on the wire like the five, or key the promise explicitly to what `meta.json` stores.

## Decisions

- 2026-08-08: **Permissions and modes collapse into one scale, and acpc always sets the mode.** Leaving `session/set_mode` unsent hands the policy to the vendor's config: measured, `acpc run claude --permissions all` produced a callee that could do nothing, because the vendor home pins `defaultMode: "dontAsk"`. The highest policy acpc offers was inert and said so nowhere.
- 2026-08-08: **A mode is described by two facts, not one.** Sol's review killed the single-scalar version and the probe agrees: `acceptEdits` auto-allows edits *and* shell writes while still delegating the destructive call, and claude's `default` runs commands its own classifier deems read-only without emitting a request. `grants` bounds what happens unasked; `delegates` says whether anything arrives. Only `grants` is a bound acpc can state, so `edit` promises what a callee may change, never that no shell ran.
- 2026-08-08: **`switch_mode` is a re-selection, not a permission kind.** The first draft classified it as read, which would have let a callee under `--permissions read` ask to enter `bypassPermissions` and be allowed — reinstating the bypass the redesign deletes, and `plan` requests a switch in normal use. The target now goes through the same ceiling as the initial selection; a refusal ends the turn naming the mode and the policy that would admit it, so the caller raises the ceiling and resumes with `continue` (variant A, chosen over parking the turn on a reverse IPC channel).
- 2026-08-08: **The `delete` rung is dropped and `other` stays unknown.** Neither claude nor codex ever emitted `delete` or `move` — a deletion arrives as `execute`, because the callee shells out. Across 48 sessions and 266 permission requests on this machine the only kinds seen were `execute`, `edit`, `switch_mode` and `fetch`. Review feedback had argued `other` was common enough that denying it made behaviour arbitrary; on this evidence it does not occur, so the `execute` rung is not widened to admit it.
- 2026-08-08: **The ceiling is inherited across re-dispatch, and the resolved policy joins the daemon target key.** A callee holding `execute` can run `acpc` itself and pick any policy for the child. `ACPC_CEILING` clamps it, but an adapter's environment is fixed at spawn while the policy varies per turn, so a warm target would hand later turns a stale ceiling. Keying by policy costs only the fixed per-target overhead — roughly 156 MB, against the ~300 MB per *session* that is paid regardless — and idle targets expire. It remains a guardrail, not a boundary: a callee with a shell can unset the variable.
- 2026-08-07: **Slice A makes `mode` part of the inspectable call resolution.** Entries may pin and inherit the vendor mode; `--mode` overrides it; the resolved value is shown with provenance, persisted in `meta.json`, reapplied by `continue`, and checked by the bypass guard before an adapter starts. Missing mode in older metadata remains unset and emits no `session/set_mode`. Mode-name validation and adapter current-mode facts stay in Slice B.
- 2026-08-07: **`prompt` stays TTY-only; asking over a non-TTY channel is rejected.** Raised after the `/dev/tty` fix, on the reasoning that if a PTY can be manufactured for a test, a pipe could serve too. It cannot: `script` *supplied* a terminal precisely because there was none. Of the three ways a non-TTY caller could answer, stdin is already the prompt source and SPEC's output contract forbids asking there (a pipe answers EOF, which is today's denial by a longer road); a classifier is `write`/`all` renamed; and delegating to the calling agent is the only coherent one but needs a control channel, paused-session state and a polling caller — a feature, not a policy tweak. The non-TTY case is already served: `_denied_summary` names the minimum policy that would have allowed what was denied, so one re-run fixes it, statelessly.
- 2026-08-07: **`v0.4.0` is not moved; the `/dev/tty` fix ships as 0.4.1.** The tag never left this machine, so moving it would be cheap — but the bug was user-visible in the build that was actually installed, and a moved tag would erase that. A patch release records what happened and supplies the reinstall the fix needs anyway.

- 2026-08-07: **0.4.0 landed on Damian's blanket go** ("leć z pracą dalej" after the pause), executed as the parked five-item checklist: ff `main`, bump + tag via `bump-my-version` (same mechanism as 0.3.0), forced reinstall, `daemon stop`, sanity dispatch. The sanity step earned its place immediately by catching the haiku-effort vendor regression.
- 2026-08-06 (0.4): exit code **4** is pinned to output-budget exhaustion. `log --follow` needed an ending distinguishable from both a clean session end (0) and a timeout (124), because the caller's next move differs: resume from the cursor rather than wait or give up.
- 2026-08-06 (0.4): `--follow`'s `--tail` replay is a **start point, not a filter** — it picks the cursor the stream begins at, and everything after it streams. Read as a filter, `--tail 0` replayed the whole transcript.
- 2026-08-06 (0.4): `--max-output` budgets the **whole follow stream**, not each page. A per-page budget would let an unbounded stream past an explicitly bounded call.
- 2026-08-06 (0.4): `steer` is **interrupt-based**, because ACP has no mid-turn injection — only `session/cancel` touches a running turn, and `session/prompt` mid-turn is protocol-undefined. The preamble is pinned in SPEC and stored verbatim in `prompt.md` so the interruption is visible on disk rather than inferred.

- 2026-08-05: **four edits to frozen files** (`smoke.sh`, `tests/mock_agent.py`), taken under the handoff's "orchestrator decides if the fix is trivially obvious" clause.   1. `smoke.sh`: `export SCRIPT_DIR`.   6. `smoke.sh` (S07): the `daemon stop` victim is now `slow:30 …`. - 2026-08-05: **open defect — a daemon can outlive its idle loop and become immortal. Must be fixed in S11.** Found while checking for leaks after S09's gate: two daemons from an earlier full-suite run were still alive 27 minutes later, holding live `mock_agent.py` children, with `ACPC_HOME` pointing at long-deleted pytest tmp dirs (`popen-gw0`/`gw1`, from `test_a_daemon_whose_socket_is_gone_stops_itself` and `test_a_daemon_that_loses_the_endpoint_retires`). `Daemon._expire_when_idle` checks `_endpoint_gone()` before anything else, and their sockets were gone with the state root, so the check would have retired them had it run at all — which points at the idle task itself having died. It is created with `asyncio.create_task` and never awaited until shutdown, and its `while True` body has no exception guard, so any raise inside it disappears silently and leaves the daemon with nothing to retire it. `kill -TERM` cleaned both up and their adapters went with them, so only the *decision* to stop is broken, not the shutdown path. **Not reproducible on demand:** 5 targeted runs of those two tests and 3 consecutive full-suite runs all left zero daemons. That also means S07's "no leaks over three consecutive runs" was never sufficient evidence — the failure is rarer than the check.
  - **Cause never established, and the comfortable explanation does not survive the timeline.** The lead's reading of the committed code is right on the merits: every operation in that loop is exception-safe, `_endpoint_identity` catches `OSError` and returns `None`, so a deleted state root should fire `_endpoint_gone()` within one `IDLE_CHECK_INTERVAL`, and there is no visible path for the task to die. The proposed explanation was that the leaked daemons ran an *intermediate* S07 code state, since a detached daemon keeps whatever was on disk when it spawned. The spawn times do not support it: both started at 21:23:38–39 and S07 was committed at 21:25:19, 101 seconds later — that is the final verification run, not an early edit. The working tree at that exact instant cannot be reconstructed, so the hypothesis is neither confirmed nor excluded — but on seeing the timeline the lead withdrew it, and **the cause is recorded as genuinely unknown.** Stage 3 should not re-litigate it from the code alone; the useful evidence now would be a recurrence, which the per-target log will explain.
  - **Fixed as hardening rather than a bug hunt** (S11, `c0d40ce`), which is the right call precisely because the cause is unknown: a done-callback on both the idle and accept loops turns any death into a recorded shutdown, so the failure class is impossible whatever caused it. It also covers a case the in-loop guard never could — `_accept_forever` legitimately returns on a socket error, which previously left a daemon alive that could no longer accept anyone. The stop reason now goes to the per-target daemon log, verified end to end, so a future occurrence leaves a post-mortem trail.
  - `_expire_when_idle`'s docstring claimed two conditions (no turn in flight *and* no owned session active) where `_busy()` checks one. Checked: the code is right and the docstring was misleading. A turn stays in `self.turns` from dispatch until `_finish` pops it, regardless of whether a client is still watching, so a detached session keeps the daemon busy on its own and the TTL cannot retire a daemon out from under one.

- 2026-08-05: **open question, blocks S11's gate and therefore S12 — smoke's `log --wait-new` timeout assertion cannot pass reliably.** `assert_eq "log --wait-new times out (124) with nothing new" "124"` runs against SLOW1, which is *live*: the mock emits 32 events at 2.0 s intervals (`SLOW_EVENT_COUNT`/`SLOW_EVENT_INTERVAL`). `poll_slow1` last advanced the cursor just before the S08 section, and roughly fifteen `uv run acpc` invocations run between there and this assertion, so several events have accumulated past the cursor by the time it fires and `--wait-new` correctly returns them with exit 0. - 2026-08-05: **`--wait-new` on a finished session blocks its full timeout and exits 124** (lead's ruling, now in SPEC). Given that, returning early buys little and costs a `cli.py` change plus assertion churn. Blocking is also the honest reading of the verb: `--wait-new` waits on *activity*, completion is `wait`'s job.
