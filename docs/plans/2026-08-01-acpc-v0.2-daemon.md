# Plan: acpc v0.2 - Persistent adapter daemon

Supersedes `2026-03-19-acpc-v0.2-daemon.md`, which was written against the npx-based v0.1
and assumed one session per daemon. Both premises are gone: adapters now launch directly
and the primary use case (orchestrator dispatching builders into parallel worktrees)
requires many sessions with different cwds at once.

## 1. Problem

v0.1 spawns a new adapter process per `acpc prompt` invocation and tears it down after.
Cold path per call (measured 2026-08-01, after npx removal and teardown fix):

| Stage | codex | claude | gemini |
|---|---|---|---|
| boot + `initialize` | 1.5s | 0.4s | 3.0s |
| `session/new` (first on process) | 2.1s | 1.3s | 0.2s |
| teardown budget | ≤1.0s | ~0s | ~0.4s |
| **overhead per call (excl. model)** | **~4.5s** | **~2s** | **~3.5s** |

Total cold call (overhead plus the warm-turn baselines in section 2): codex ~6.5s,
claude ~5s, gemini ~5.5s. Multi-turn (`--last`/`-s`) pays the full cold path every turn
plus `session/load` history replay.

Root cause: ACP agents are designed to be long-lived (one spawn, many prompts over the
same stdio pipe). acpc v0.1 treats them as one-shot.

## 2. Measurements that shaped the design

Warm-adapter probe (`session/new` x4 on one process, different cwds, zero tokens):

| adapter | boot+init | session/new #1 | session/new #2-4 |
|---|---|---|---|
| codex-acp | 1471 ms | 2087 ms | 784 / 513 / 474 ms |
| claude-agent-acp | 425 ms | 1336 ms | 1624 / 1377 / 1680 ms |
| gemini --acp | 2968 ms | 165 ms | 69 / 46 / 45 ms |

Three profiles: codex pays ~1.5s of one-time lazy init on the first `session/new` and
0.5-0.8s after; claude pays ~1.4s *every time*, warm or not, so its win is reusing a
live session rather than a live adapter; gemini's cost is entirely CLI boot. The daemon
must therefore hold both a warm adapter *and* a table of live sessions —
one-session-per-daemon (the old plan) would force a restart per worktree.

Warm-turn baseline (live session, trivial "Reply with just OK" prompt, default models):

| agent | turn latency (3 samples) |
|---|---|
| codex | 1.5 / 2.1 / 2.4 s |
| claude | 2.7 / 2.7 / 4.0 s |
| gemini | 2.0 / 2.1 / 2.5 s |

A warm turn is model-dominated; adapter-side overhead on a live session is IPC only.
Combining the two runs above (they used different prompts, so treat these as
±0.5s estimates, not guarantees):

| agent | cold call | warm, fresh session | warm, continued |
|---|---|---|---|
| codex | ~6.5 s | ~2.8 s | ~2.1 s |
| claude | ~5.1 s | ~4.5 s | ~3.2 s |
| gemini | ~5.7 s | ~2.3 s | ~2.3 s |

Claude barely gains on fresh sessions because its `session/new` is a process spawn
(see the memory probe below); its win is continuations.

Adapter-behavior probes (2026-08-01, run before Phase 1 because three design
premises depended on them; scripts in scratchpad, tiny prompts):

**Concurrency on one connection** — two prompts in flight, two sessions:

| adapter | per-prompt | wall time | serial equivalent | attribution |
|---|---|---|---|---|
| codex-acp | 2586 / 3532 ms | 3534 ms | ~6118 ms | correct per `sessionId` |
| claude-agent-acp | 2485 / 2536 ms | 2536 ms | ~5021 ms | correct, notifications interleaved |
| gemini --acp | 3024 / 3439 ms | 3439 ms | ~6463 ms | correct |

All three multiplex genuinely in parallel, no cross-session text leakage. The
per-target `serialize` fallback flag from the earlier draft is therefore dropped.

**Two prompts on the *same* session** — this is the important one:

| adapter | behavior |
|---|---|
| claude-agent-acp | queues them (advertises `agentCapabilities._meta.claudeCode.promptQueueing: true`) |
| codex-acp | **cancel-and-replace**: first prompt returns in 251 ms, `stopReason: "cancelled"`, zero output, no JSON-RPC error |
| gemini --acp | cancel-and-replace, first prompt killed in 33 ms |

So the per-session FIFO queue is a correctness requirement, not an optimization:
without it two `-s SAME_ID` dispatches would silently annihilate one another, and
the only trace would be a `stopReason` the caller may never inspect.

**`session/cancel`** — reliable everywhere, and non-destructive:

| adapter | cancel latency | stopReason | late chunks | session reusable |
|---|---|---|---|---|
| codex-acp | 16 ms | cancelled | 1 | yes (next turn took 11.4 s) |
| claude-agent-acp | 5 ms | cancelled | 0 | yes (2.2 s) |
| gemini --acp | 70 ms | cancelled | 1 | yes (3.8 s) |

Cancel never killed the adapter and never poisoned the session, which is what makes
a daemon-safe `--timeout` possible (section 5). The late-chunk tail is 0-1 frames.

**cwd validation** — adapters cannot be trusted with it:

| adapter | nonexistent cwd at `session/new` | cwd deleted after creation | relative cwd |
|---|---|---|---|
| codex-acp | accepted silently | answers normally | accepted (`.` and `relative/path`) |
| claude-agent-acp | `-32602 cwd does not exist` | `-32603 Path ... does not exist` | rejected, absolute required |
| gemini --acp | `Directory does not exist` | answers normally | `.` accepted, rest rejected |

Only claude catches a worktree deleted under a live session. acpc must validate cwd
itself (absolute + exists) on both the fresh and the resume path — this also closes two
v0.1 holes: `--cwd` is checked only for existence (`cli.py:109`, `click.Path(exists=True)`),
so a **relative** path passes and is resolved against acpc's own cwd before being handed
to adapters that disagree about whether that is legal; and nothing re-checks cwd on the
`-s` / `--last` path.

**Cost of a long-lived adapter** (20 `session/new` on one process, zero tokens, RSS of
the whole process tree):

| adapter | baseline | after 20 sessions | per session | pids |
|---|---|---|---|---|
| gemini --acp | 448 MB | 469 MB | ~1 MB | 2, flat |
| codex-acp | 256 MB | 1.59 GB | ~66 MB | 3 → 24 |
| claude-agent-acp | 120 MB | 17.4 GB | ~850 MB | 1 → 176 |

The cost is not ACP session state. `claude-agent-acp` spawns a full `claude
--output-format stream-json` subprocess *plus the entire configured MCP server fleet*
on every `session/new` and never reaps any of it; codex spawns one MCP bridge process
per session (~58 MB) and keeps a single shared `codex app-server`; gemini spawns
nothing per session. Magnitudes depend on the local MCP config, the spawn-and-never-reap
pattern does not. It also explains claude's flat ~1.4 s `session/new`: that is a
process start, not a session.

Consequence for the design: in v0.1 this memory dies with the process after every call.
A daemon turns it into permanent memory. How much of it can be reclaimed depends on the
protocol version, and this is where the earlier version of this plan was wrong.

**Session lifecycle capabilities** (measured 2026-08-01 against `agent-client-protocol`
0.11.0; the numbers above were taken against 0.8.1, which has no session-close method):

| adapter | advertises `close` | `close` accepted | RSS reclaimed | pids reclaimed | `fork` | `resume` |
|---|---|---|---|---|---|---|
| claude-agent-acp | yes | ok | 1753 → 125 MB | 18 → 1 | yes | yes |
| codex-acp | yes | ok | 496 → 474 MB | 6 → 6 | no | yes |
| gemini --acp | no | n/a | n/a | n/a | no | no |

`session/close` exists in ACP 0.11.0 (`ClientSideConnection.close_session`, negotiated
through `AgentCapabilities.sessionCapabilities.close`) and **claude reclaims its entire
process tree on close**, which removes the single worst cost in the table above. Codex
advertises the capability, accepts the call and frees nothing; its sessions are cheap
enough (~66 MB, one pid) that this is a slow leak rather than a cliff. Gemini advertises
no session lifecycle at all.

So the daemon closes sessions when the adapter supports it, and keeps the capacity guard
and recycle policy (section 6) as the backstop for adapters that do not. Measured with
2-3 sessions and no prompts; a session that has done real work may hold more, and
codex's non-reclaim may be partly allocator retention rather than a true leak. Neither
caveat changes the design, because claude's 18 pids → 1 is too large to be measurement
noise.

**Credential handling** (strace on `openat`, init → 2 prompts):

| agent | where credentials live | when read |
|---|---|---|
| claude | `~/.claude/.credentials.json` (access token ~hours, refresh token ~15 days) | 8 opens, all during boot/`session/new`; zero during either prompt |
| codex | OS keyring (`cli_auth_credentials_store = "keyring"`) | no file to trace |
| gemini | `GEMINI_API_KEY` from the environment | read once at process start |

So a rotated credential is picked up by a *new* session (claude) or only by a *new
process* (gemini), never mid-session. A daemon that outlives a token refresh keeps
using the old one. This is what the max-age recycle in section 6 is for.

## 3. Use cases

1. **Orchestrator → builders**: many `acpc prompt` dispatches into parallel worktrees,
   different cwds, different permission levels, possibly different models. Primary case.
2. Interactive multi-turn without cold start per turn (`--last` hits a live session).
3. Skill orchestration: several `acpc prompt` calls from one skill reuse the adapter.
4. Headless backend for custom frontends (later; out of v0.2 scope).

## 4. Architecture

```
acpc prompt codex "task A"  (cwd=wt-a)     acpc prompt codex "task B"  (cwd=wt-b)
      |                                          |
      v                                          v
  daemon_client.py ---- Unix socket, NDJSON ---- daemon_client.py
              \                                 /
               v                               v
          daemon.py  (one process per TARGET, spawn-on-first-use, idle TTL)
               |
               |  single ACP connection over stdio (persistent)
               v
          adapter (codex-acp)
               |  live-session table:  session_id -> (cwd, state)
               |    sess-123 (wt-a)   (prompt A running)
               |    sess-456 (wt-b)   (prompt B running concurrently)
               v
          agent (LLM)
```

Key decisions:

| Decision | Why |
|----------|-----|
| **Daemon keyed by target, not agent** | Planned named targets (`codex-luna` etc. with own `CODEX_HOME`/env) are separate adapter processes with separate auth. Today target == agent identity; the key must not assume that stays true. Socket/lock filenames derive from the target name. |
| **Many live sessions per daemon, keyed by session_id** | Section 2. ACP supports it natively; this is what removes the old plan's CWD limitation and per-daemon serialization. `cwd` is just a `session/new` parameter. How many is bounded by memory, not by a constant (section 2); a measured capacity guard decides (section 6). |
| **Fresh session by default; reuse only on explicit `--last`/`-s`** | Matches native CLI semantics agents are trained on: `claude -p` is fresh unless `-c`/`--resume`, `codex exec` is fresh unless `exec resume`. Implicit cwd-based reuse (earlier draft) would silently bleed context between unrelated dispatches from the same directory - an orchestrator has no way to notice. The daemon is a performance cache, never a semantics change. |
| **Concurrent prompts on different sessions, FIFO per session** | Parallel builders must not queue behind each other (section 2). The per-session queue is mandatory for the opposite reason: codex and gemini answer a second concurrent prompt on one session by silently cancelling the first. |
| **acpc validates cwd, not the adapter** | codex never validates it, gemini only at `session/new` (section 2). Absolute + exists is checked client-side before a fresh session and before every resume; a resumed session whose cwd is gone is evicted with a usage error instead of running the agent in a directory that no longer exists. |
| **Permissions and model are per-request, not per-daemon** | Enforcement is client-side code (`AcpcClient.request_permission`) running in the daemon; the active prompt carries its own level. This requires turning `AcpcClient` into a demultiplexer first (section 6, item 1.4b) — the v0.1 instance holds one output handler and one level for its whole lifetime. Model set per session by reusing `_try_set_model`, whose only path since ACP 0.11 is `set_config_option` (`session/set_model` was removed from the protocol; Phase 0 deleted the fallback). A session that advertises no model config option — which is what `session/load` returns — cannot have its model set at all: that is a warning and a failure, never a silent success, or the daemon would record a `current_model` the adapter never adopted. |
| Unix domain sockets + NDJSON | Local IPC standard; file permissions (`chmod 600`) are the security model. Named pipes for Windows in v0.3 behind `DaemonTransport` ABC. |
| `fcntl.flock(LOCK_EX\|LOCK_NB)` on lock file | Kernel releases on crash; PID files alone are unsafe (PID reuse). |
| Spawn on first use, idle TTL exit | Right pattern for dev tools (Gradle, acpx). No systemd. |
| **Default-on with automatic fallback** | Any daemon-path failure (spawn timeout, stale socket, protocol error) → stderr warning + direct spawn, same exit-code contract; a daemon bug can never block a call. Opt-out: `--no-daemon` / `ACPC_NO_DAEMON=1`. Opt-in instead would require env plumbing in every skill/orchestrator prompt and would leave the daemon path unexercised. |

### New files

| File | Responsibility |
|------|----------------|
| `src/acpc/ipc.py` | `DaemonTransport` ABC + `UnixSocketTransport` (bind/accept/connect/cleanup) |
| `src/acpc/daemon.py` | Daemon process: socket server, adapter lifecycle, session table, per-session queues, idle TTL |
| `src/acpc/daemon_client.py` | Client: connect, auto-start, stale detection, stream response into `OutputHandler` |

### Changes to existing files

| File | Change |
|------|--------|
| `cli.py` | `--no-daemon` on prompt (daemon is the default); `-c`/`--continue` alias for `--last` (claude-code muscle memory; `--last` already matches `codex exec resume --last`); `acpc daemon status`, `acpc daemon stop [target]`; `--print-session-id` (with `-o`); `--cwd` + continuation = usage error |
| `runner.py` | `run()` routes through daemon_client by default; direct spawn on any bypass rule (section 5). `_spawn_agent`, `_drain_notifications`, `_try_set_model` and `kill_process_tree` reused by daemon.py as-is; `_STOP_REASON_EXIT` is **not** reused for `cancelled` (section 5) |
| `sessions.py` | `STATE_DIR` constant → `state_dir()` reading `ACPC_STATE_DIR` (item 1.0); daemon-hosted sessions record the daemon pid + `daemon: true` |
| `client.py` | `AcpcClient` becomes a per-session demultiplexer (item 1.4b); v0.1 single-consumer behavior stays the direct path's |

## 5. Behavior

**Default (daemon, transparent):**
```bash
acpc prompt codex "task"                # auto-starts daemon, FRESH session (like codex exec)
acpc prompt codex "task B"              # same daemon, another FRESH session (~0.5-0.8s, no boot)
acpc prompt codex --last "follow-up"    # continues task B: live session, IPC + model time only
acpc prompt codex -s SESS_A "tweak it"  # continues task A by id, even though B was last
# daemon exits after 300s idle (ACPC_DAEMON_TTL)
```

Semantics are identical to v0.1 and to the native CLIs (`claude -p`, `codex exec`):
every call is a fresh conversation unless continuation is explicit. The daemon only
changes how fast that happens.

**Automatic bypass (silent or warned, never an error):** the client uses direct spawn
when any of these hold:

1. `--no-daemon` flag or `ACPC_NO_DAEMON=1` (explicit opt-out; also the debug path
   with full adapter stderr)
2. Windows (v0.2 has no transport there) - silent, no stderr line at all
3. Interactive permissions requested (`--permissions prompt` on a TTY) - the daemon
   cannot proxy the prompt; stderr note
4. Daemon path fails: spawn timeout, connect failure after stale cleanup, protocol
   error - stderr warning `[acpc] daemon: unavailable (<reason>), running direct`,
   then direct spawn. A daemon bug degrades performance, never correctness.
5. Daemon is at its memory ceiling and refuses new sessions (section 6) - stderr note
   `[acpc] daemon: at capacity, running direct`. Continuations into sessions it already
   holds still go through the daemon.

**Management:**
```bash
acpc daemon status          # per target: PID, uptime, sessions (id, cwd, state, started)
acpc daemon stop codex      # kill one daemon (adapter tree included)
acpc daemon stop            # stop all
```

### Session resolution per prompt

Client sends `cwd` + optional session ref; daemon resolves in order:

1. Explicit `-s SESSION_ID` → live in table? use it (fast path). Not live? `session/load`,
   add to table.
2. `--last` / `-c` → client resolves the id from the local session store (as today),
   then rule 1.
3. No ref → always `session/new(cwd)` on the warm adapter, add to table. Never reuse
   implicitly.

Session ids still get recorded in the client-side session store on `prompt_done`, so
`--last` keeps working across daemon restarts (falls back to `session/load`).

Continuation rules (external-review finding, gpt-5.6-terra 2026-08-01):

- A resumed session keeps its original cwd. `--cwd` combined with `-s`/`--last`/`-c` is
  accepted when it resolves to the session's recorded cwd and is a usage error (exit 2)
  on a genuine mismatch: `session cwd is <recorded>, --cwd says <given>`. Orchestrators
  template one command string and pass `--cwd` unconditionally, so rejecting the
  *correct* combination would turn a no-op into an outage; silently ignoring a
  *wrong* one would hide where the agent actually ran.
- For orchestrators that need the session id programmatically: `--json` already ends
  with a meta event carrying it (the key is `"acpc": "session_ended"`, `output.py:127`;
  the v0.1 plan document writes it as `{"event": ...}` and is wrong). Additionally
  `--print-session-id` prints just the id as the first stdout line, valid only with
  `--quiet -o FILE` — the one combination where stdout carries nothing else, since
  `--json` streams NDJSON and text mode streams chunks. Any other combination is a
  usage error.
- `cwd` is validated by acpc before anything is sent to the adapter: it must be
  absolute and exist. On resume, the session's recorded cwd is re-checked; if the
  worktree is gone the session is evicted from the table and the call fails with
  exit 2 (`session cwd no longer exists: <path>`). Two of three adapters would
  otherwise answer as if nothing happened (section 2).

### Timeout and Ctrl+C in daemon mode

Killing the adapter is not available any more (it serves other sessions), and it is
not needed: `session/cancel` is reliable and leaves the session usable (section 2).

1. `--timeout` fires (or Ctrl+C) → client sends `cancel` over the socket
2. Daemon issues `session/cancel`, drains the short late-chunk tail, replies
   `prompt_done` with `stop_reason: cancelled`
3. Client exits 124 (timeout) or 130 (Ctrl+C); the daemon and the session survive
4. If the daemon does not answer within `_CANCEL_GRACE` (2 s — three orders of
   magnitude above the measured 5-70 ms), the daemon itself is broken, not slow: the
   client reads the PID from the lock file, kills the daemon tree, and still exits
   124/130. The exit-time guarantee never depends on the daemon behaving.

The first turn after a cancel can be slow (codex took 11.4 s in the probe), so no
health check may treat a post-cancel session as hung below ~15 s.

Because three different situations all end as `stop_reason: cancelled`, the daemon
tags each with `cancel_source` and the client does **not** reuse
`runner._STOP_REASON_EXIT` (which maps `cancelled` to 130 unconditionally,
`runner.py:49`):

| `cancel_source` | Meaning | Exit |
|---|---|---|
| `client` | our own `cancel` — the client knows whether it came from `--timeout` or Ctrl+C | 124 or 130 |
| `daemon` | shutdown or recycle | 1, `daemon shutting down` |
| `unrequested` | nobody asked; another prompt superseded this one | 1, `prompt superseded on this session` |

Every other `stop_reason` keeps the v0.1 mapping.

## 6. Design details

### Daemon lifecycle

1. **Auto-start**: daemon mode on and `{state_dir}/run/{target}.sock` missing/stale →
   client spawns `Popen([sys.executable, '-m', 'acpc.daemon', target], start_new_session=True)`
2. **Readiness**: daemon binds socket → client polls connect every 100ms, timeout 15s.
   A cold burst (orchestrator firing N dispatches at once) has every client spawning a
   daemon; the flock arbitrates. Losers find the lock held, exit quietly with status 0
   and no output, and their clients just keep polling until the winner binds. Nothing
   is retried at the client level and no client ever sees an error from this.
3. **Lock**: `flock()` on `{state_dir}/run/{target}.lock`; contents: PID, socket path,
   acpc version, target, start time
4. **Socket**: `chmod 600` right after `bind()`
5. **ACP init**: spawn adapter via `_spawn_agent` with `cwd` = the daemon's own state
   dir, never a caller's worktree (per-session cwd travels in `session/new`; a daemon
   outlives the worktrees it serves), `initialize()` once; sessions created lazily per
   request (section 5)
6. **Serve**: accept clients, route requests to per-session tasks, stream
   `session_update` back, `_drain_notifications` before each `prompt_done`
7. **Idle TTL**: no active prompt and no connected client for `ACPC_DAEMON_TTL`
   (default 300s) → graceful shutdown. Independently, the capacity guard,
   `ACPC_DAEMON_MAX_AGE` or an auth error put the daemon into *recycling* (no new
   sessions, finish what is running, exit when idle)
8. **Shutdown**: reject queued requests with `shutting_down` → close ACP connection →
   teardown identical to runner.py (EOF, `_EXIT_TIMEOUT`, `kill_process_tree`) →
   remove socket + lock
9. **Log**: `{state_dir}/log/{target}.log`, truncated at daemon start, carrying daemon
   events and the adapter's stderr. Direct mode shows adapter stderr on the terminal;
   in daemon mode it would otherwise vanish, and "reproduce it with `--no-daemon`" only
   works for problems that reproduce. `daemon status` prints the path.

### Session table

- Key: session_id. Value: cwd, created_at, last_used, state (idle/active), queue,
  `session_response` (the `session/new` result, which `_try_set_model` needs to find the
  model config option — `runner.py:266-277`), `current_model` (`None` until first set;
  a request whose model matches skips the call), `mode`, connected client socket,
  permission level, replay flag.
- **No session cap.** An LRU cap would be pure bookkeeping: eviction frees nothing on the
  adapter side (section 2) and only pushes a still-resumable id onto the slower
  `session/load` path. Memory is bounded by the capacity guard below, which is the only
  mechanism that actually reclaims anything.
- `AcpcClient` in the daemon is a **demultiplexer**, not the v0.1 single-consumer client:
  `session_update`, `request_permission` and the file operations all dispatch on their
  `session_id` argument to the per-session record. The v0.1 instance fields `output`,
  `permission_level` and `replaying` (`client.py:114-118`) move into that record; leaving
  `replaying` process-wide would blank out every concurrent session's output during any
  `session/load` replay.
- Per-session FIFO queue, max depth 4, `{"type": "queued", "position": N}` updates.
  One prompt at a time per session; different sessions run concurrently. Mandatory:
  codex and gemini silently cancel the running prompt when a second arrives on the
  same session (section 2). A prompt arriving at a full queue is rejected with
  `{"type": "error", "message": "session queue full (4 waiting)", "exit_code": 1}` and
  the client does **not** fall back to direct spawn — a direct spawn cannot reach this
  session.
- Safety net for the same class of bug from outside the daemon (another process holding
  the same session id, or a future adapter that supersedes anyway): a `prompt_done`
  with `stop_reason: cancelled` that the daemon did not itself request is reported as
  an error (exit 1, `prompt superseded on this session`), never as an empty success.
- Global cap of 4 concurrent prompts across all sessions
  (`ACPC_DAEMON_MAX_CONCURRENT`); prompts above the cap wait in arrival order and get
  the same `queued` updates as the per-session queue.

### Closing idle sessions

The primary reclaim mechanism, for adapters that support it.

- At `initialize`, record `AgentCapabilities.sessionCapabilities.close`. That single
  boolean decides everything below; never call `session/close` on an adapter that did
  not advertise it.
- A session idle for `ACPC_DAEMON_SESSION_TTL` (default 10 min) is closed:
  `session/close`, drop it from the table, unregister it from the demultiplexer.
  A closed session is **not** dead to the caller: its id still resumes through
  `session/load`, just cold. That is the whole point of preferring this over recycling,
  which takes every sibling session down with it.
- Never close a session with an active or queued prompt, and never close the session a
  connected client is attached to.
- `session/close` failure is not fatal: log it, leave the record, let the capacity guard
  handle the consequences.
- Measured effect (section 2): claude returns to its 125 MB baseline and reaps its whole
  process tree; codex accepts the call and frees nothing; gemini does not support it.
  So this reclaims exactly where the cost is, and the guard below covers the rest.

### Capacity guard and recycle

The backstop, for what closing cannot reclaim: codex accepts `session/close` without
freeing anything, gemini has no session lifecycle at all, and adapters differ by three
orders of magnitude in what a session costs (section 2). Rather than hard-coding a
per-adapter session count that goes stale the moment someone changes their MCP config,
the daemon measures what it actually holds:

1. Before every `session/new`, sample the adapter tree's RSS (`/proc/<pid>/status` for
   the process group; `ps` on macOS).
2. Above `ACPC_DAEMON_RSS_MAX` (default: 25% of `MemAvailable` from `/proc/meminfo`,
   floor 2 GB; the env var overrides with an absolute value in MB) the daemon does **not** create the
   session: it replies `capacity`, marks itself for recycle, and the client falls back
   to direct spawn with `[acpc] daemon: at capacity, running direct`. Worst case is
   v0.1 behavior, which is exactly the bounded-memory behavior we have today.
3. Existing live sessions keep serving prompts — continuations, the main win for
   claude, stay fast while the daemon drains.
4. **Recycle** = stop accepting new sessions, finish active prompts, exit when idle.
   Next call respawns cleanly. Triggers: RSS ceiling, `ACPC_DAEMON_MAX_AGE` (default
   4 h, comfortably under observed token lifetimes), or an auth-shaped adapter error.
   Before recycling on the RSS ceiling, close every closable idle session first and
   re-sample; recycling is what happens when that is not enough or not supported.

No per-adapter constants: the same ceiling allows dozens of codex sessions and a
handful of claude ones, and gemini never approaches it.

### Stale daemon detection (client, on connect)

1. Socket exists? No → spawn
2. Lock file exists? No → remove stale socket → spawn
3. `flock(LOCK_EX|LOCK_NB)` succeeds? Yes → daemon dead → clean up → spawn
4. PID from lock → `os.kill(pid, 0)` → gone → clean up → spawn
5. acpc version in lock ≠ ours → `shutdown` over the socket, wait up to 10s for the old
   daemon to drain and exit, then SIGTERM the pid if it is still there → spawn new
6. `connect()` → ECONNREFUSED → clean up → spawn
7. Socket missing but the lock's pid is alive (someone deleted the socket file under a
   running daemon): SIGTERM that pid, clean both files, spawn. Without this rule the
   client would spawn a daemon that loses the flock, exits quietly, and leave the caller
   polling a socket nobody will ever bind until the 15s readiness timeout

### IPC protocol (internal, will change without notice)

NDJSON over the socket. Not a public API.

```jsonl
-> {"type": "prompt", "text": "...", "cwd": "/abs/path", "permissions": "write",
    "model": "gpt-5.6-sol/high", "mode": null, "session_id": null, "output_mode": "text"}
<- {"type": "session_started", "session_id": "sess-123", "reused": "new"}
                                            # new | live (in the table) | loaded (session/load)
<- {"type": "capacity", "rss_mb": 3100}      # instead: no new sessions, client goes direct
<- {"type": "session_update", ...}          # ACP passthrough, streamed
<- {"type": "permission", "session_id": "sess-123", "kind": "edit",
    "title": "write sentinel.txt", "outcome": "deny"}  # client prints it via output.py:42
<- {"type": "queued", "position": 1}        # only if session busy
<- {"type": "prompt_done", "stop_reason": "end_turn", "session_id": "sess-123"}
<- {"type": "error", "session_id": "sess-123", "message": "adapter connection lost",
    "exit_code": 1}                         # client exits with exit_code, prints message
<- {"type": "shutting_down"}                # queued prompt rejected before it ran;
                                            # client retries once via direct spawn

-> {"type": "cancel", "session_id": null, "reason": "timeout"}  # or "interrupt"
   # session_id null = "my active prompt on this connection" (timeout, Ctrl+C)
   # session_id set  = "the active prompt on that session, from any connection"
   #                   (`acpc stop -s ID`, which connects fresh and owns nothing)
<- {"type": "cancel_ack", "session_id": "sess-1", "accepted": true}  # management path only
<- {"type": "prompt_done", "stop_reason": "cancelled", "cancel_source": "client",
    "session_id": "sess-123"}               # cancel_source: client | daemon | unrequested

-> {"type": "status"}                       # for `acpc daemon status`
<- {"type": "status", "pid": N, "uptime_s": N, "log": "/path/to/target.log",
    "sessions": [...]}

-> {"type": "shutdown"}
<- {"type": "bye"}
```

- `permissions` is applied to that prompt only: the daemon's `AcpcClient` evaluates the
  active request's level. Interactive prompting (`--permissions prompt` on a TTY) is not
  available in daemon mode; the daemon behaves like non-TTY (deny + stderr hint to use
  `--no-daemon`). The client warns and falls back to direct spawn when the user asked
  for interactive permissions with daemon mode on.
- The decision **must reach the caller's stderr**, not only the daemon log. `AcpcClient`
  evaluates permissions inside the daemon, so a direct `stderr_permission()` call there
  writes into the log and the user sees a tool silently do nothing. That is why the
  `permission` frame exists: every decision the daemon makes on a caller's behalf is
  reported to that caller, on both outcomes. Denial that is enforced but invisible is the
  failure mode this frame prevents.
- `model` and `mode` are set on the session when they differ from what the record holds,
  skipped when unchanged (`_try_set_model`, `runner.py:280`; `session/set_mode`,
  `runner.py:573`). Dropping `--mode` silently in daemon mode is not an option: it
  changes what the agent is allowed to do.
- The `[acpc] still running...` heartbeat (`runner.py:249`) stays in the **client**, driven
  by its own timer: the daemon may be serving other sessions, so only the client knows
  how long this caller has been waiting.
- Client Ctrl+C and `--timeout` both send `cancel` over the socket (daemon stays alive)
  instead of the runner's kill path; escalation to killing the daemon only if it fails
  to answer within `_CANCEL_GRACE` (section 5).

### Error recovery

| Scenario | Behavior |
|----------|----------|
| Adapter crashes (broken stdio) | Daemon fails active prompts with `error` (exit 1), cleans up, exits. Next prompt auto-starts fresh |
| Daemon crashes | Kernel releases flock → next client detects stale → respawns |
| Client dies mid-prompt | Daemon cancels that prompt (`session/cancel`), session stays live for others |
| Queued client disconnects | Removed from queue, remaining get position updates |
| Client timeout / Ctrl+C | `cancel` → `session/cancel` → `prompt_done(cancelled)`, session survives; daemon unresponsive → client kills it via lock PID and still exits 124/130 |
| Prompt cancelled without the daemon asking | Reported as error (exit 1, `prompt superseded on this session`), never as empty success |
| Resume against a deleted cwd | Client-side check → session evicted from the table, exit 2 with the path |
| Concurrent cold starts | flock picks one daemon; losing spawns exit quietly, their clients keep polling |
| Shutdown with non-empty queues | Reject all queued with `shutting_down`, finish nothing, exit |

### v0.1 session commands under a daemon

`runner.py:554` records each session with the adapter's pid and `cli.py:330` implements
`acpc stop` as `kill_process_tree(pid)`. With a shared adapter that would kill every
other live session — exactly what the timeout design avoids.

- A daemon-hosted session records the daemon's pid plus `daemon: true`.
- `acpc stop -s ID` on such a session sends `cancel` over the socket instead of killing
  anything; `acpc stop <agent>` cancels all its daemon-hosted sessions and leaves the
  daemon running. Ending a daemon is `acpc daemon stop <target>`.
- `acpc status` marks those sessions `(daemon)`.

### Cross-platform

v0.2: Linux + macOS. `DaemonTransport` ABC ships with only `UnixSocketTransport`;
Windows v0.3 adds `NamedPipeTransport` + an `msvcrt.locking()` wrapper with no
daemon-logic changes (CPython on Windows has neither `AF_UNIX` nor `fcntl`, so there is
no shortcut). On Windows in v0.2 the client takes bypass rule 2 and runs direct,
silently. Direct spawn has been portable since v0.1 (`_process_group_kwargs`,
`kill_process_tree` via taskkill, guarded signal handlers), though untested on real
Windows/macOS machines.

## 8. Test strategy

Three layers, as in v0.1:

```
Layer 1: unit (no processes)         — ipc, session table, queues, stale detection, lock
Layer 2: integration (mock agent)    — full lifecycle, deterministic, no tokens
Layer 3: live (@pytest.mark.live)    — real adapters, timing, orphan detection
```

Every daemon test must assert after completion: **no orphan processes, no leftover
socket/lock files, exit happened via the expected path**.

Timing assertions:

| Assertion | Threshold | Catches |
|-----------|-----------|---------|
| Cold first prompt | < 15s | broken spawn, stuck readiness poll |
| Warm, live session (mock) | < 1s | daemon not reused |
| Warm, new cwd (live, codex) | < 3s | session table not reused, re-init per call |
| Idle TTL exit | TTL ± 1s | stuck accept loop |
| Queue position update | < 500ms | notification delay |
| Cancel round-trip | < 2s | measured 5-70ms; a regression here means the escalation path is being exercised for no reason |

## 9. Risks

Only what survives a fully executed plan belongs here. If the answer to a danger is a
numbered item with an acceptance test, it is a task and lives in section 7.

**Residual — still true after everything in section 7 passes:**

| Risk | Why it stays open | What we do about it |
|------|-------------------|---------------------|
| codex leaks process trees per session | Upstream defect we cannot fix, and unlike claude it is not addressable by `session/close`: codex advertises the capability, accepts the call and frees nothing (~66 MB and one pid per session, section 2). Closing reclaims where the cost is worst, the guard bounds what is left | Close idle sessions where supported, recycle at the RSS ceiling and degrade to v0.1 behavior above it (section 6); reproducer reported upstream (section 11) |
| codex credential rotation on a long-lived daemon | Keyring-backed, so unlike claude and gemini it left no traceable file access. Deliberately not investigated: no outcome would change the design, since max-age recycles the daemon well below any token lifetime | Accept as a stated assumption; 5.5 watches for auth failures in daily use |

**Carried by plan items instead of by this table:** silent supersede on a shared session →
1.6, 1.6b, 3.6; stale-daemon detection edge cases → 2.3 extended to the full

| Adapter can't multiplex concurrent prompts | Measured false on all three adapters (section 2); `serialize` fallback deleted |

| A daemon's memory can only be reclaimed by killing the adapter | False since ACP 0.11.0: `session/close` exists and claude reclaims its entire process tree (1753 → 125 MB, 18 → 1 pid). Phase 0 migrates, item 1.13 uses it. Held only against 0.8.1 |

## 10. NOT in v0.2

- Interactive permission prompting through the daemon (use `--no-daemon`)
- Frontend protocol (HTTP, SSE, WebSocket), remote access
- Windows named pipes (v0.3; `DaemonTransport` ABC ready)
- Auto-restart of a crashed adapter within a running daemon (daemon exits, next prompt respawns)
- Session fork (`opencode run --fork`, `claude --fork-session`): useful orchestrator
  primitive (prepare context once, fork for N builders). ACP has it, and the probe
  (section 2) answered which adapters do: **claude yes, codex no, gemini no**. Deferred
  to v0.3 on scope, not on knowledge — it needs its own CLI surface and a memory
  measurement of what a fork actually costs, and claude alone does not justify that in
  v0.2
- `--mode` is carried through (section 6); `--env` is not. `cli.py` never populates
  `RunConfig.env` today, so nothing regresses — but if it ever does, a shared warm
  adapter has a fixed environment and `--env` must become bypass rule 6
- `--env` filtering (separate backlog)
